Authorization design

Slack connect: one click, and nothing passes through our servers

The old setup asked every user to create their own Slack app, tick twelve scopes and paste an xoxp- token into Keychain by hand. This replaces all of it with a single Connect click — while keeping the property that matters: no Taiv server sits anywhere in the path, because there is no Taiv server at all.

1The flow

Three participants, and a fourth that is conspicuously absent. Every arrow below is either inside the user's own machine or a direct call to slack.com.

  1. PKCE pair is generated locally. A random code_verifier, and its SHA-256 hash as the code_challenge. The verifier never leaves this process — that is the whole trick.
  2. Browser opens the authorize URL carrying the public client_id, the challenge, a CSRF state, and user_scope. Not scope: Slack forbids bot scopes on desktop redirects, and asking for one fails with an opaque error.
  3. The user clicks Allow — the only thing they ever have to do.
  4. Slack redirects to http://localhost:4318/slack/callback, a listener inside the cockpit. This hop happens entirely inside the user's machine. It is also why no server is needed to receive the callback.
  5. The code is exchanged directly with slack.com, sending the code_verifier instead of a client_secret. Only the process that started the flow holds the verifier, so an intercepted code is worthless.
  6. Slack returns the user token plus a refresh token.
  7. Verified, then stored. auth.test runs before the write — a stored-but-dead credential is worse than none, because the daemon only discovers it mid-scan.

2Why there is no client_secret

A client_id shipped inside a desktop app is readable by anyone, so it cannot prove identity on its own. PKCE replaces that proof with a per-attempt secret that never travels.

Without PKCE

Needs a server

The token exchange requires a client_secret. Embedding it in a downloadable app leaks it, so the exchange has to happen on a backend — which then handles every user's tokens, and becomes exactly the third-party hop this design refuses.

With PKCE

No server, no secret

The challenge goes out at authorize time; the verifier only at exchange time. Slack: refreshes “do not require a client_secret because they are intended to be used on a public client.” Enabled 2026‑03‑30.

Consequence

Staying serverless is not only a privacy stance. Google's CASA security assessment applies to apps that can reach restricted data “from or through a third-party server”. A local-only design should avoid a paid annual assessment on the Gmail side — adding a token broker would forfeit that.

3What rotates, and what breaks

The hand-pasted token never expired. A PKCE token does, and that is the one real regression to design around.

access_token~12 hoursRefreshed silently inside a 60s buffer by readSlackToken()
refresh_token30 daysFull re-consent. The cockpit must surface a Reconnect state, not fail mid-scan
legacy xoxp-neverReturned untouched, no network call — existing installs keep working
Edge case

A laptop closed for a month

Comes back with a dead refresh token and needs the user to click Connect again. Detect it and show it; silence here reads as a broken product.

Undocumented

Refresh response shape

Slack documents the nested authed_user shape for the initial exchange but not for a user-token refresh. The parser accepts nested or top-level, and both are tested.

4One-time setup, on our side only

Done once, by us, forever. Slack issues tokens only to a registered app — the app is a registration record, not a server, and no data ever passes through it.
