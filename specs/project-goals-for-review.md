# PrivateSecretary — 项目目标文档(供外部 AI 审核 / 制定方案)

> **这份文档的用途**:交给另一个 AI 做**独立审核 + 出实施方案**。
> 它包含:我们要什么(目标与已锁定决策)、现状为何做不到(经代码与数据核实的证据)、
> 从真实数据算出的准确率基线、拆解出的工程问题、以及一批**已被实证否决的方案**
> (请不要再提议它们)。
>
> **读者须知**:本项目最高优先级是**准确性**。任何"看起来聪明但会降低精度"的建议
> 都会被拒绝。请在给方案时明确指出你的每条建议**如何被度量**。

## 1. 产品目标(用户原话,只有两件事)

1. **自动监控聊天记录 → 生成准确的 Calendar Event**:准确的**时间**、准确的**地点**、准确的**参会人**。
2. **自动总结每天最高优先级的待办,防止忘事**:24 小时监控聊天记录且**动态更新**。
   待办包含待办描述 + action item。目前 AI 需要自动处理的子动作只有两个:
   - 用 MCP **一键创建 Jira Ticket**,带项目描述 + assignee。
   - 根据项目上下文,**自动生成邮件草稿(AI draft)**。

用户评价现状:"目前的项目这几个简单的功能都做的不是很好。"

用户对方法的要求原话:
> "我需要的是最好的结果、最准确的结果。即使你删掉整个 codebase 也可以。**Goal first, then approach**。"
> "我希望的是一个**真正智能、可以自己一直进化**的 Agent 秘书。"(明确反对"一堆代码层面的硬逻辑")

## 3. 现状:为什么做不到(全部经代码/数据核实)

### 3.1 架构层面的根因

| # | 问题 | 证据(文件:行) |
|---|---|---|
| P1 | **所有精度关键字段都是自由生成的文本**。日历标题/时间/地点/参会人、待办内容,由一次 LLM 调用凭空写出 | `relay/proc/draft.ts` + `draft-prompt.ts` |
| P2 | **没有时间解析器,连"今天是几号"都没注入**提示词。时间靠硬编码的 上午/下午/晚上 → 时段表**猜** | `draft-prompt.ts:170-173`;draft 系统提示词里**完全没有时区声明** |
| P3 | `missingInfo` **从不校验 start/end 能否解析**,也不校验 start < end | `relay/core/action-item.ts:142-150` |
| P4 | **参会人绕过了已有的 ASK-not-GUESS 解析器**。模型自己写邮箱,唯一防线是正则;写错但格式合法的邮箱照样通过,只有名字则被**静默丢弃** | `relay/proc/execute.ts:329-336`;`recipient-resolver.ts` 只用于回复收件人 |
| P5 | attendees / location 是 **optional**,不完整的事件也能被批准 | `action-item.ts:146-149` |
| P6 | **Jira executor 根本不存在**。"一键 Jira"实际是人跑的 prose skill,assignee 是自由猜测 | `execute.ts` 只分发 task/ignore/calendar/slack/gmail/wechat |
| P7 | **待办对象不存在**。每次 refresh 都 `randomUUID()` + `created_at: now()` 重造,并**删除**上一轮的卡片 → 身份、年龄每 10 分钟归零。所有"碎片化/陈旧/已订会议又冒出来"的故障都是它的下游 | `refresh.ts:147-151`;`scan-loop.ts:613-618` |
| P8 | **任务身份 = 标题的哈希**(`sha256(normalizeTitle)`)。标题漂移→碎片化;标题撞车→错误合并。**这就是被明令拒绝的"相似度匹配",且是最脆的一种** | `consolidate.ts` `stableTaskId` |
| P9 | **消失 = 删除**,没有记录、没有原因 → "多久才消失"无法度量、无法审计 | 502 条 shadow 日志中的 action id 仅 173 条还在 state 里 |
| P10 | **已设计好的精度内核被搁置**。`specs/anchor-pipeline.md` 定下"关联只由显式 anchor 建立、绝不靠模型语义直觉、错连趋近 0";但只有确定性校验器建成并测试,**被任何代码引用零次** | `relay/core/anchors.ts` |

### 3.2 从真实数据算出的准确率基线(本次实测)

365 条历史 action item,按类型统计 `executed/(executed+rejected)`:

| 类型 | executed | rejected | 已决策 | **精度** |
|---|---|---|---|---|
| `reply` | 16 | 79 | 95 | **0.168** ← 84% 被拒 |
| `task` | 56 | 70 | 126 | **0.444** |
| `ignore` | 92 | 17 | 109 | 0.844 |
| `calendar` | 8 | 2 | 10 | 0.800 |
| `relay` | 5 | 0 | 5 | 1.000 (n=5) |

**结论:绝不能用一个总数来衡量"准确率"**——把 0.168 和 0.844 平均掉只会掩盖问题。**必须从第一天起按类型分开度量。**

置信度校准(同一份数据):`task` 在 0.9 桶的通过率 0.94(n=31),well-ordered;而 `reply` 在 0.9 桶通过率 **0.00**(n=5),**完全无效甚至反向**。→ 现有 `confidence` 不可作为跨类型的自动化阈值;但 `task` 类型加 0.85 门槛是一个**今天就能度量的免费精度提升**。

### 3.3 标签资产比预期弱,而且正在自我删除

| 项 | 实测 |
|---|---|
| 决策时间戳 `decided_at` | **0 条**(完全没有) |
| 编辑内容 `edited_by_user` | **1 条**(365 中) |
| 拒绝原因 `reject_reason` | **1 条**(168 次拒绝中) |
| `outcomes[]` 行数 | **8 条** |
| `MAX_TERMINAL_ACTIONS` | **500**(`relay/io/state.ts:113`)→ 目前 345 条终态,**约一个月后标签集开始静默自我删除** |

**这是最紧急的工程债**:唯一能证明"变准了"的原料正在流失,且缺少时间戳与原因,信息密度极低。

被低估的资产:109 条 `ignore` 决策 = 92 个确认的真阴性 + **17 个确认的触发器假阴性**(人说"不,这个不该忽略")→ 免费的召回侧 ground truth。

## 4. 从目标反推的工程问题

| # | 工程问题 | 本质 |
|---|---|---|
| **E1** | 这到底算不算一件事(三类之一)? | **社交判断**(是否指向我、是否已被处理、是否只是客套),**不是**字符串解析 |
| **E2** | 时间/地点/参会人/assignee 怎么才准? | **有据抽取 + 何时该弃权(待确认)** |
| **E3** | 24h 追踪一件事的生命周期(出现→更新→消失) | **时序状态追踪 / 信念修正**;需要一个**能跨 tick 存活的对象** |
| **E4** | 用户每次编辑/否决/确认如何变成**永久**能力提升 | **自我进化**(用户的核心诉求) |
| **E5** | 怎么证明它真的变准了 | **可度量评测 + 防回归** |
| **E6** | 因人/因场景的个性化 | 学习偏好与人际规范(persona 层已有基础) |

> **关键约束:E5 是 E4 的前提。** 没有可度量的准确率,任何自我修改都是盲改,且直接违反 D1。
> 现状是"最近十个 commit 都是盲修",因为没有任何东西可度量。

## 5. 已被实证否决的方案(请不要再提议)

调研了 20+ 篇论文与生产实践,以下**看起来很对但有硬证据反对**:

| 被否决的方案 | 反对证据 |
|---|---|
| **模型自我反思 / self-refine / "你确定吗"** | 无外部信号的自我纠正**会变差**:CommonSenseQA 75.8%→**38.1%**,GSM8K 也降(arXiv 2310.01798)。被质疑时模型翻答案 **36–95%**(sycophancy)。**反思只允许挂在"人的 diff"上** |
| **一个会自我改写的全局提示词 / 自编辑 CLAUDE.md** | 实测**比不学习更差**:累计编辑成本 57,915 vs 不学习 48,269;按上下文检索的对症记忆 32,974(CIPHER, NeurIPS 2024, arXiv 2404.15269) |
| **GEPA / MIPROv2 等提示词自动优化器** | 需 **678–6,858 次 rollout**、150/300 训练验证集。我们只有 365 条 + 订阅制 CLI,付不起且验证集太小不可信 |
| **多智能体辩论(debate)** | 同等算力下**不如**简单 self-consistency,且多花 **2.1–3.4× token** |
| **让 LLM 自由判断"这是不是在拜托我"** | 多方对话 addressee 识别:GPT-4o **80.9%** vs 多数类基线 **80.1%**(等于没学到);预测下一说话人 **46%**,**低于随机**(arXiv 2501.16643)。→ 必须用机械特征 |
| **让 LLM 做日期运算** | 失败不是"差一点"而是**平均差 100 天以上的类别性崩溃**(PRIMETIME)。→ LLM 只输出原话 + 形式表达式,由确定性库解析 |
| **口头置信度(0–100 自评)作为门控** | 系统性过度自信,黑盒 AUROC 仅 **0.52–0.61**。且 **Claude 不暴露 logprobs** |
| **向量/嵌入相似度做"相关"或"同一件事"** | 项目已明令拒绝且正确:相似度引擎会**幻觉出"相关"**。注意 Graphiti 的 dedup 正是这个——**取它的双时间模型,弃它的相似度解析层** |
| **现有的 `stableTaskId = sha256(标题)`** | 这**就是**要拒绝的相似度匹配,最脆的形式。两个方向都错:漂移→碎片化,撞车→错误合并 |
| **直接执行 LLM 发出的 delete/update** | DELETE/UPDATE 是 prompt-only LLM 最差的操作(Memory-R1)。→ **模型提议,确定性代码准入(两把钥匙)** |
| **LLM-as-judge / 成对 A/B 作为发布门** | 自我偏好偏差;位置偏差在重排后翻转 10–30% 判定;冗长度评分与长度相关 r=.87(人类 .44)。→ **门必须是"对照人的真实历史决策做回放"** |
| **用 LLM 判断可信度来防记忆投毒** | 实测放进 82 条里 **54 条是恶意的**(信任分 1.0)。→ 只能用**结构化 provenance** |
| **单一"准确率"数字** | 0.44 和 0.17 平均掉比没有数字更糟 |
| **`pass@k`** | 对"每天早上都必须对"的产品是自我安慰。→ 用 **`pass^k`**(k 次全过才算过) |
| **从 approve/skip 日志推召回率** | **结构上不可能**:日志只覆盖系统选择呈现的条目(logged bandit 选择偏差)。召回只能靠独立标注集 |

**安全性必须单独强调**:本产品读 Slack/Gmail —— **攻击者可写的输入**。纯发消息即可对 agent 记忆注入,成功率 **98.2%**(MINJA, NeurIPS 2025)。因此必须:**A 类 = 用户操作**(可产生规则);**B 类 = 消息内容**(只能作为"关于世界的事实"被引用,**永远不能变成策略**,永不自动提升)。

## 附:项目技术背景(便于定位)

- 运行形态:本地 daemon(`scripts/run-notify.ts` → `relay/proc/scan-loop.ts runScanTick`),8–12 分钟一 tick;本地 cockpit web app(`relay/cockpit/`,port 4317)做三分屏审阅。
- 推理:通过 **Claude Code 订阅制 CLI**(`relay/proc/llm-claude-cli.ts`,`claude -p`),**零 API 成本**;无微调、无梯度、不假设有 embedding 服务。
- 现有 daemon 阶段:PHASE 0 扫描(无 LLM)→ 2 起草 → 4 合并 → 5 refresh(重读线程)→ 6 排序(A/B/C/D)→ 7 persona 更新。LLM 调用在**锁外**,只有短暂的 `commitUnderLock` 写状态。
- 关键规格文档:`specs/anchor-pipeline.md`(精度内核,已冻结契约)、`specs/persona-v3.md`(记忆层 + R1)、`specs/daily-todo.md`(Today 设计)、`specs/action-item-engine.md`。
- 测试:vitest,508 passing。有若干**强制回归测试不得删除**(dedup-survives-restart、no-double-execute、reply-requires-approval、R1-manual-survives-llm-update)。
- 微信为测试来源:本地 sqlcipher 解密(`relay/io/wechat-cli.ts` 驱动 `ylytdeng/wechat-decrypt` MCP),钉在 WeChat 4.1.8.x;**个人 1:1 无官方发送 API**(与 D3 不自动发送一致)。
